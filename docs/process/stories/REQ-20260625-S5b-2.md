# REQ-20260625-S5b-2: apply + confirm-token (RL-4) + conflict serialization (RL-5), transition-only

## Description

As the local operator, I want to apply a triage finding (recording the `Aplicado`
transition on the triage card), so that the RETRO loop reflects which issues have
been acted on — with a mandatory two-step human-in-the-loop gate for framework-routed
findings (RL-4) and a conflict block when a sibling already applied the same target
file (RL-5).

Smoke flow: POST `/api/triage/:id/apply` with a framework-routed `finding_id` and no
token → 403 CONFIRM_REQUIRED carrying `confirm_token` in `detail` → re-POST with that
token (against a TEMP vault) → 200 with the card's `Status` cell mutated on disk to
`applied` → replay the same token → 403 (used; single-use enforced).

Builds on the FROZEN S5b-1 WriteFirewall additively. TRANSITION-ONLY: the write is
always `triage_record` via `writeTriageRecord` + `setFindingCell` / `setFrontmatterDecision`.
No `agents/*.md` content write this cut.

## Acceptance Criteria

### Backend — Token (RL-4)

1. [ ] `backend/src/services/confirmToken.ts` exports `mintConfirmToken(scope: TokenScope): string`
       and `verifyConfirmToken(token: string, scope: TokenScope, now: number): "OK" | "INVALID" | "EXPIRED" | "USED" | "SCOPE_MISMATCH"`.
       `TokenScope` is `{ id: string; finding_id: string; target_file: string }`.
2. [ ] `CONFIRM_SECRET` is `crypto.randomBytes(32)` generated once at module load (singleton);
       it is NEVER written to logs, `.env`, environment variables, or included in any response.
3. [ ] Token format: `base64url(payloadJson) + "." + base64url(HMAC_SHA256(CONFIRM_SECRET, payloadJson))`
       where `payloadJson = JSON.stringify({ id, finding_id, target_file, issued_at })`.
       No external JWT library — Node `crypto` only.
4. [ ] Verification step 1: split at `.`; recompute `HMAC_SHA256(CONFIRM_SECRET, decodedPayload)`;
       compare with `crypto.timingSafeEqual`. Any mismatch → `"INVALID"`.
5. [ ] Verification step 2 (scope binding): the payload's `{ id, finding_id, target_file }` MUST
       equal the current request's `{ id, finding_id }` and the finding's current `target_file`
       (re-read from disk at apply time). Any field mismatch → `"SCOPE_MISMATCH"`.
6. [ ] Verification step 3 (TTL): `now - payload.issued_at > TTL_MS` (TTL_MS = 120 000 ms, a named
       module-level constant `CONFIRM_TOKEN_TTL_MS`) → `"EXPIRED"`.
7. [ ] Verification step 4 (single-use replay defense): a module-level `Set<string>` named
       `usedTokens` stores HMAC digest strings of consumed tokens. If the HMAC digest is already
       in `usedTokens` → `"USED"`. On a successful apply the route layer calls
       `markTokenUsed(hmacDigest: string): void` (exported from `confirmToken.ts`); entries whose
       `issued_at` is past TTL are pruned lazily (on each `markTokenUsed` call) to keep the set
       bounded. `markTokenUsed` is the ONLY path that writes to `usedTokens`.
8. [ ] Any `verifyConfirmToken` result other than `"OK"` is collapsed to `"CONFIRM_REQUIRED"` at
       the service layer; the route maps `"CONFIRM_REQUIRED"` → 403 + fresh token (via
       `mintConfirmToken`); NO write occurs.

## API Contract

### POST /api/triage/:id/apply

**Request:**
```json
{
  "finding_id": "P2",
  "confirm_token": "eyJpZCI6IjIwMjYtMDYtMDYtc2llX3YyIiwiZmlu..."
}
```
`finding_id` is required (card-level apply → 400). `confirm_token` required only for
framework-routed findings; omit for project-routed.

**Response 200:**
```json
{
  "doc": {
    "id": "2026-06-06-sie_v2",
    "date": "2026-06-06",
    "project": "sie_v2",
    "decision": "applied",
    "applied": true,
    "findings": [
      {
        "id": "P2",
        "target_file": "rules/no-matter-stringify.md",
        "routing": "framework",
        "status": "applied"
      }
    ]
  }
}
```

**Response 403 CONFIRM_REQUIRED** (framework finding, token absent/invalid/expired/used):
```json
{
  "code": "CONFIRM_REQUIRED",
  "message": "Framework apply requires a confirm token.",
  "detail": {
    "id": "2026-06-06-sie_v2",
    "finding_id": "P2",
    "target_file": "rules/no-matter-stringify.md",
    "confirm_token": "<freshly minted HMAC token>",
    "expires_at": "2026-06-25T10:02:00.000Z"
  }
}
```

**Response 409 CONFLICT** (sibling already applied same `target_file`):
```json
{
  "code": "CONFLICT",
  "message": "A sibling finding has already applied this target file.",
  "detail": {
    "target_file": "rules/no-matter-stringify.md",
    "conflicting_card": { "id": "2026-06-10-sie_v2", "finding_id": "P1" }
  }
}
```

**Response 404:** `{ "code": "NOT_FOUND", "detail": { "id": "..." } }`

**Response 400:** `{ "code": "BAD_REQUEST", "detail": { "id": "..." } }` — finding_id absent,
finding not yet routed, or invalid body.

**Response 403 PATH_FORBIDDEN:** `{ "code": "PATH_FORBIDDEN", "detail": { "id": "..." } }`

**Response 500 WRITE_FAILED:** `{ "code": "WRITE_FAILED", "detail": { "id": "..." } }`

## Technical Notes

- `confirmToken.ts` is the ONLY file with module-level in-memory state in the backend (`CONFIRM_SECRET`,
  `usedTokens`). Documented for Phase 5.5 reviewer. The secret is not a constructor arg — it is a
  per-process singleton that rotates on restart (acceptable: local single operator; a restart mid-confirm
  merely re-prompts).
- `RetroState` is app-owned (LL-008 exception, same precedent as `DriftState` / `Governance` z.enums).
  It is used for service-layer transition logic ONLY; it is NOT used to retype the externally-owned
  `TriageFinding.status` / `TriageDoc.decision` fields.
- `ApplyFailed` in `RetroState` is logic-only — it is NOT persisted to the card (the card is
  byte-unchanged on a failed write per the S5b-1 atomic-rename guarantee). It surfaces as 500 WRITE_FAILED.
- RL-5 conflicting-state definition: a sibling finding is conflicting when `F_prime.status === "applied"` OR
  `F_prime`'s parent doc's `decision === "applied"`. Non-blocking siblings: `"deferred"`, `"rejected"`,
  `"pending"` / blank. Architect may widen to block `"pending"` siblings at Phase 3.
- Stack-profile gap (carried from S5b-1): no `express.md` / `react.md` stack profile in
  `.claude/stack-profiles/`. File layout derived from the live S1–S5b-1 source tree.
- Import path for tests: `import { applyTriage } from "../services/triageActions.js"` (`.js` extension,
  ESM — verified against `backend/src/routes/triage.test.ts` import pattern).
- Import path for `confirmToken` in tests: `import { mintConfirmToken, verifyConfirmToken, markTokenUsed } from "../services/confirmToken.js"` (verified: same layer, same ESM pattern).
- Phase 6.5 (E2E): deferred. The confirm modal is a 2-step UI flow; Phase 6 integration + 6.8 smoke cover it.
- Phase 6.7 (Deployment): skipped (local single-user, no Docker/CI surface).
- Rule T6 applies: S5b-2 is security-relevant and interdependent with the firewall; run `make test` after S5b-1 BEFORE starting S5b-2.
