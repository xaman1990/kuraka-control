### Headline 1 — the adversarial freeze killed FOUR latent holes **before any code** (3rd consecutive cycle)

The architect (Phase 3) was **APPROVED_WITH_MINOR** and, in the freeze, **closed four
latent BLOCKER-class holes** — all rooted in the **permissive nullable contract
fields** (`TriageFinding.{id,routing,target_file}` and `TriageDoc.decision` are all
`z.string().nullable()`, the LL-008 trade-off):

1. **Null `target_file` scope-collapse** — a confirm-token whose scope binds
   `target_file = null` would collapse the cross-target binding (a token for one gold
   target could apply another). Frozen fix (§1.5): the service rejects a framework (or
   project) apply with a null/blank `target_file` as `BAD_REQUEST` **before** minting
   or verifying any token; `TokenScope` is built ONLY from non-null strings.
2. **RL-5 null-id self-exclusion** — `F.id === this.finding_id` alone is unsafe when
   `F.id` is null. Frozen `isSelf` predicate (§2) requires `F.id != null` AND
   `doc.id === this.id` before the equality, so a null-id sibling is correctly treated
   as a distinct finding.
3. **`timingSafeEqual` length-guard** — `crypto.timingSafeEqual` **throws** on
   unequal-length buffers; an attacker-supplied short/long signature would crash the
   verify. Frozen fix (§1.4): a length check BEFORE `timingSafeEqual`, returning
   `INVALID`.
4. **`usedTokens` `Set` → `Map`** — the replay store had to be a `Map<hmacHex,
   issued_at>` (not a `Set`) so expired entries can be lazily pruned and the store
   stays bounded by TTL × apply-rate.

All four were caught by the architect **empirically reasoning about the live nullable
contract** before a line of code. **This is the THIRD consecutive cycle where the
adversarial freeze caught a major class of defect pre-code** (S4: the Windows-drive
`path.isAbsolute` traversal bypass; S5b-1: the `matter.stringify` data corruption;
S5b-2: the four nullable-field holes). All three were on security/write-critical
seams, all three were pure freeze value (zero rework cost). **This is no longer
"emergent" — it is the project's demonstrated highest-leverage defect filter and
should be promoted to a named process strength / an explicit architect checklist**
(§4 #1, §6).

### Headline 2 — TWO honest process findings the orchestrator/reviewers surfaced

This cycle is the most instructive in the project precisely because **two gate gaps**
were exposed by mechanisms OTHER than the gate that "should" have caught them:

1. **The orchestrator's live-verify caught a runtime bug green `make test` did NOT.**
   After Phase 4, the orchestrator ran the apply path against a temp vault and found
   that applying an **already-applied** finding made `setFindingCell` a no-op
   (`newText === raw`) which was then **mis-mapped to 404 NOT_FOUND** (the same no-op
   signal the freeze used for "unknown row"). The green `make test` at the end of
   Phase 4 did **not** catch it **because the apply tests are written in Phase 6,
   AFTER implementation** — so Phase 4's "green" was green against the *pre-existing*
   suite, not against apply behavior. The fix (skip the write / return 200 on an
   idempotent already-applied no-op) was applied in 4a; the **code review then found
   the SECONDARY case** (a genuinely short/unknown row that ALSO produces
   `newText === raw` but SHOULD be 404). Both were resolved (no-op already-applied →
   200; unknown short row → 404). **Lesson:** the orchestrator's temp-vault live-verify
   after Phase 4 is **high-value for write surfaces** and should be made an **explicit
   guardrail**, not a happy accident (§4 #3, §6). It is also direct evidence to
   reconsider the Phase-4-then-Phase-6 test ordering **for write surfaces** (§3, §4 #3).

2. **`make test` does NOT run typecheck — a real gate gap, ~3 cycles latent.** A
   pre-existing **S4** `as string` cast in `projectLayer.test.ts` was a `tsc --noEmit`
   error that **vitest tolerated** (vitest transpiles per-file, does not type-check the
   graph). It survived ~3 cycles undetected because **`make test` runs vitest, not
   `tsc`**. The S5b-2 code review surfaced it (the reviewer ran typecheck). This is a
   real CI-equivalent gap: a class of error (type breaks in test files, or any file
   vitest happens not to choke on) can ride green for cycles. **Propose LL-014 +
   adding `typecheck` to the test gate (or a `make check` that runs lint + typecheck +
   test)** (§4 #2, §5, §6).
