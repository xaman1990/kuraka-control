## 1) Summary

- **Total iterations:** **low-to-medium for an L cycle.** **Zero GATE0 loops**
  (PASS first pass, proactive census — LL-010). **One Phase-5 CHANGES_REQUIRED
  loop** (1 BLOCKER + 3 frontend MINORs), fixed in a single tight
  backend+frontend parallel pass (~90 s wall). **Zero user-correction loops on
  the deliverable.** The security review added **zero** loops — it PASSed.
- **Main causes of the one loop:** a **single real correctness BLOCKER** —
  symlink **double-classification** in `walkLayerTree`. On Node 22 a symlink
  dirent reports `isFile() === false && isDirectory() === false`, so the walk's
  two filter predicates (one for files, one for dirs) **both** failed to claim
  it as a normal entry yet the symlink still matched both emit paths → every
  symlink was emitted **twice**. Fixed with `stat`-based single-classification
  (no descent preserved, containment untouched).
- **Estimated preventable iterations:** **~0.5 loop.** The BLOCKER was *largely*
  a genuine platform footgun (Node-22 dirent semantics), not negligence — but it
  is **LL-011-adjacent**: the freeze specified the *containment* mechanism to the
  byte while leaving the *tree-walk symlink classification* mechanism less
  precisely pinned (see §3 story-refiner). A one-line "classify by `stat`, never
  by dirent type bits, for symlinks" in the freeze would likely have pre-empted
  it. So: partially preventable, cheap to fix, and now codified (§5, LL-012
  candidate).

The orchestrator scaled the pipeline **up** correctly for the first time —
recognizing that a client-path-driven file read is exactly the surface that
earns a dedicated 5.5 — and the call paid off in **proof**, not in new findings
(see §3 systemic). The headline risk (traversal) was frozen as a copy-ready
6-step algorithm with 10 named invariants (SEC1–SEC10), and the freeze *actively
paid for itself* twice: once when the architect caught a Windows-drive bypass
(SEC2) before any code, and once when the security review traced all ten
invariants verbatim through the implementation and confirmed each live.

## 1b) Did the dedicated Phase 5.5 pay off? (yes — by PROVING the seam, with a clean division of labor)

This is the cycle's marquee question, and the answer is an evidenced **yes** —
but the value is subtler than "it caught a bug." It did **not** catch a CRITICAL
(there was none to catch). Its value was **independent confirmation of the
containment seam under adversarial tracing**, and a **clean division of labor**
with the general 6D review:

### The dedicated 5.5 paid off as PROOF, not as a net

- The security-reviewer traced the frozen 6-step resolver **verbatim** against
  the implementation and then **confirmed every adversarial vector live**:
  `../` traversal, symlink-escape, symlink-loop, NUL byte, Windows-drive (`C:\`),
  too-large, binary — **all → 403/404/400, none read the file.** It verified the
  leak-avoidance invariant (403 body carries **only `{rel}`**, never the resolved
  absolute path — SEC5/SEC10) and scanned for secrets (**0 found**). Result:
  **PASS, no CRITICAL/HIGH**, 2 LOW/INFO (a `stat`-vs-`lstat` comment nit on the
  symlink `size_bytes`).
- For a feature whose **entire reason to exist is a client-controlled fs read**,
  "we traced the attack surface and ran every vector live and it held" is the
  deliverable. A general code review *asserting* containment is correct is weaker
  evidence than a dedicated adversary *failing to break it*. The freeze's SEC1–10
  checklist gave the reviewer an exact target, so the review was a verification
  pass, not an exploration — efficient (62K tokens, 18 tool uses) and conclusive.

### The division of labor with the 6D review worked — and is the strongest argument both phases earn their keep on an L story

The two Phase-5 gates caught **different** things, in their lanes:

- **Security (5.5) PASSed the containment seam** — the thing it exists to guard
  (traversal/symlink-escape/leak). It found no security defect because the freeze
  had already hardened the seam (SEC2 Windows-drive guard added in Phase 3).
- **General 6D review (5) caught the correctness BLOCKER** — the symlink
  **double-emit** in the tree walk. That is **not a security bug** (a duplicated
  visible node escapes nothing, reads nothing out of bounds); it is a
  **correctness** defect in the *display* path. The 6D reviewer's mandate
  (correctness, not just security) is exactly what surfaced it.

This is the cleanest demonstration in five cycles that **the two reviews are not
redundant on a high-risk story**: one proved the security seam; the other caught
a non-security correctness bug the security pass would not (and should not) have
been looking for. On S2/S3 (read-only, single trust boundary) folding 5.5 was
correct and cost nothing. On S4 (client-path fs read) un-folding it was correct
and the 6D+5.5 split earned both their tokens. **The Rule-0 risk scaling — fold
when low, un-fold when the surface is a client-controlled fs read — is validated
in both directions now.**

**Verdict: the dedicated 5.5 was worth it.** Not because it found a CRITICAL, but
because (a) it converted "the containment code looks right" into "every
adversarial vector was traced and run live and rejected," which is the only
acceptable evidence for this surface, and (b) the 6D/5.5 division of labor caught
two genuinely different defect classes. Keep the rule: **un-fold 5.5 whenever the
story reads/writes a path that originates from the client.**

### story-refiner (Phase 2, with 2.5 folded) — strong, LL-011 applied (one assessed gap)

- **What went right:** Applied **LL-011** exactly where it was born to apply:
  stated the **exact 6-step containment algorithm** as resolved AC (B10), not a

- **What failed — the one honest finding:** the story specified the symlink
  **resolver** behavior precisely (B7: "symlinked dirs not followed; symlinked
  files re-validated on read via realpath"; B10 Steps 3–4 realpath both sides)
  but did **not** specify the **tree-walk classification mechanism** — i.e. *how*
  `walkLayerTree` decides a dirent is a file vs a dir when the dirent is a
  **symlink** (whose `isFile()`/`isDirectory()` are both false on Node 22). B7
  says "symlinked files appear as file entries" but not "classify by `stat`, not
  by dirent type bits." That under-specification is the proximate seam of the

- **Assessment (is this an LL-011 violation or an acceptable implementation
  miss?):** **Borderline, leaning "LL-011 extension," not a clean miss.** LL-011

  implementation. Dirent classification of a symlink **does** have >1 reasonable
  implementation (dirent type bits vs `stat`/`lstat`), and the wrong one is a
  silent footgun on Node 22. So it is squarely in LL-011's spirit. **But** the
  miss is more forgivable than the S2/S3 hedges: those left an *obvious* binary
  choice unstated (yaml-vs-JSON), whereas this required knowing a **non-obvious
  platform fact** (Node-22 symlink dirent semantics) to even see the fork. It is
  fair to call it **half platform-footgun, half mechanism-precision gap.** The
  right remedy is not to scold the refiner but to **codify the platform fact** so
  the next fs-walk story names the classification mechanism by reflex (LL-012
  candidate, §5).

## 4) Systemic Issues

1. **The dedicated 5.5 paid off — and so did the Rule-0 *direction* of the
   change.** S2/S3 correctly **folded** 5.5 (read-only, single trust boundary);
   S4 correctly **un-folded** it (client-path fs read). The orchestrator now has
   a validated two-way rule: fold when low-risk, un-fold when the surface reads a
   client-originated path. The 5.5 added zero loops (PASS) and its value was
   **proof of the seam + a clean division of labor with the 6D review** (6D
   caught the correctness BLOCKER; 5.5 proved the security seam). Log as a
   **positive** systemic signal: *both* Phase-5 gates earn their keep on an
   L-complexity client-fs story.

2. **code-reviewer (and now security-reviewer) wall-time is firmly out-of-band
   (recurring, performance axis).** The 6D reviewer ran ~54 min (S1 ~25, S3 ~58.5,
   S4 ~54 — **3 of 5 cycles slow**, S2 the only in-band run); the 5.5 reviewer
   also ran ~48 min on its first outing. Tokens stay proportionate every time —
   this is a **latency**, not a token, defect. It has now crossed every
   reasonable recurrence bar. **Recommendation:** feed both Phase-5 reviewers a
   **context digest** (Rule T1: the frozen schema / SEC1–10 checklist +
   changed-file list + the specific invariants to verify) so they read/grep less.
   This is a standing **pattern-detector** input (§ pattern-detector).

3. **Node-22 fs-walk classification footgun (new — feeds LL-012).** The BLOCKER
   came from a real platform fact: a symlink dirent reports neither `isFile()`
   nor `isDirectory()` true on Node 22, so classifying tree entries by dirent
   type bits silently mis-buckets (here: double-emit) symlinks. Any future fs-walk
   (S6 telemetry tree? governance file pickers?) inherits this hazard. **This is a
   genuine lesson, not a cosmetic nit** — codify it (§5) so the next walk
   specifies `stat`-based classification by reflex.

4. **The mechanism-hedge thread (LL-011) held for the *resolver*, leaked for the
   *walk*.** LL-011 was applied **correctly and visibly** to the containment
   algorithm (B10 stated the exact 6 steps; the architect confirmed, didn't
   re-resolve) — a clear win and the first cycle to test LL-011 since it was
   written. But the *same* discipline was **not** applied to the tree-walk symlink
   classification, which is where the BLOCKER lived. The thread is therefore
   *partly* suppressed (resolver) and *partly* recurred (walk) — an important
   nuance for pattern-detector: LL-011 works when the fork is obvious; the walk
   fork was non-obvious (platform-fact-gated), which is exactly the LL-012 gap.

5. **Standing debts unchanged (none recurred as defects):** canonical vault
   `VERSION` file (S2 #1), sidebar active-nav prefix-match (S2 #2), dev-README
   `:5174`/`BACKEND_PORT` note (open since S1, now **5 cycles** of the same
   `BACKEND_PORT=5184` workaround). None blocked S4; all still cheap and
   batchable. SMOKE-S4 also re-notes the LOW symlink `size_bytes` `stat`-follows
   cosmetic (no action — read re-validates via realpath).

## 5) Workflow Improvements + Proposed Lessons

1. **Un-fold Phase 5.5 whenever the story reads/writes a client-originated
   path.** S4 validated the rule in the un-fold direction (S2/S3 validated the
   fold direction). The dedicated security review is conclusive and cheap **when
   fed a frozen invariant checklist** (SEC1–10). Make "client-supplied path → fs"
   an explicit Rule-0 trigger for un-folding 5.5. (Application note, no prompt
   change — the orchestrator already did this correctly here.)

2. **Freeze a security-invariant checklist (SEC#) with a "where" column for any
   security-critical seam.** SCHEMA-FROZEN-S4's SEC1–SEC10 table is what made the
   5.5 a fast verbatim verification instead of an exploration. Encourage the
   architect to freeze **named invariants + locations**, not only the algorithm,
   for any path-containment / auth / write-firewall seam. (Extends the S2/S3
   "freeze invariants, not just shapes" note to the security axis.)

3. **The new genuinely-new lesson: fs-walk entry classification must specify
   symlink handling explicitly (LL-012 candidate).** Unlike S3's `--radius-card`
   gap (a project-specific cosmetic → review-check), this is a **process/platform
   root-cause pattern** that will recur on every fs-walk: dirent type bits are
   **insufficient for symlinks** on modern Node, and the wrong classification is a
   silent footgun. This rises to an LL (not just a review-check) because it is a
   reusable, root-cause, cross-story rule — exactly the bar S3 set for what
   deserves an LL. Proposed below.

```markdown
## LL-012 — Un walk del filesystem que clasifica entradas DEBE especificar el manejo de symlinks: los bits de tipo del dirent son insuficientes

- **REQ origen**: REQ-20260624-S4-project-layer-browser (walkLayerTree)
- **Síntoma**: En Node 22 un dirent de symlink reporta `isFile() === false &&
  isDirectory() === false`. El tree-walk clasificaba por los bits de tipo del
  dirent con dos predicados (uno para archivos, uno para dirs); un symlink no fue
  reclamado como entrada normal por ninguno y terminó **emitido dos veces**
  (BLOCKER de Phase 5, primer BLOCKER desde S1). No es un bug de seguridad
  (la contención del resolver estaba intacta) — es un bug de *correctitud* en el
  camino de *display*.
- **Causa raíz**: LL-011 obliga a declarar el *mecanismo* cuando un paso tiene
  >1 implementación razonable, pero el fork aquí era **no obvio**: requería saber
  un hecho de plataforma (la semántica del dirent de symlink en Node moderno) para
  siquiera ver la bifurcación. El freeze pinneó el mecanismo de *contención*
  (resolver, Steps 3–4 realpath) al byte, pero dejó la *clasificación del walk*
  sin mecanismo explícito.
```
