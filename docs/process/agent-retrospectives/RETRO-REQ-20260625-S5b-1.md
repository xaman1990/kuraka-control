### Headline — the adversarial freeze killed a data-corruption BLOCKER **before any code**

The story (AC9 / AC11, Technical-Notes lines 326–329) prescribed re-assembling the
mutated card via **`matter.stringify(parsedBody, data)`**. The architect verified
empirically that `matter.stringify(content, data) !== raw`: it **coerces
`date: 2026-06-06` → an ISO `Date` timestamp**, re-quotes `source`, and reflows
`tags: [retro-triage]` to block style. **Every single write action would have
silently corrupted the card's `date` (and reflowed its frontmatter) on disk.**
On the *first vault-write surface*, that is the worst-possible class of bug —
silent, persistent, on the source of truth. The freeze (§4, §5 of
`SCHEMA-FROZEN-S5b-1.md`) replaced it with a **surgical raw-line rewrite**:
`split("\n")`, replace only the one target table cell (or the one
`decision:`/`applied:` frontmatter line), re-join — never round-tripping the
document through gray-matter. `matter()` is used *only* to skip past the
frontmatter block when locating the table, never to re-serialize.

**This is the second consecutive cycle where the adversarial freeze caught a major
defect before a line of code was written** (S4: the Windows-drive `path.isAbsolute`
bypass — SEC2; S5b-1: the `matter.stringify` corruption). On S4 the catch
prevented a *traversal* gap; here it prevented *silent data corruption of the
vault*. Both were pure freeze value — zero rework cost, caught at the cheapest
possible gate. This is now a **process strength worth codifying** (§3, §4).

### Did the dedicated Phase 5.5 pay off? (yes — by proving every WRITE vector is contained)

The security-reviewer traced the WriteFirewall containment algorithm **verbatim
to the frozen 6-step algorithm** and **confirmed every adversarial write vector
live in a throwaway temp vault**: `../` traversal, absolute path, **Windows-drive
prefix**, NUL byte, the `_TEMPLATE.md` regex bypass, nested `sub/x.md`, and a
**symlinked `retro-triage` dir** — **all → 403 PATH_FORBIDDEN, none wrote a
file.** It verified the **single-writer** invariant holds (the grep finds only
`writeFirewall.ts` in production source), the **atomic `.tmp`+rename** procedure
(original card never truncated-in-place), the **byte-preservation** of the raw-line
rewrite (date preserved — the BLOCKER fix), and the **leak-avoidance** invariant
(403 body carries only `{id}`, never the absolute path). Result: **PASS, no
CRITICAL/HIGH**, 2 LOW/INFO (an `id`-guard `..` belt-and-suspenders nit with no
exploit; the documented symlinked-dir residual), **0 secrets**. For the first
write surface, "we traced every write vector and ran each one live in a disposable
vault and none touched disk outside `retro-triage/`" is exactly the deliverable —
and it confirms the Rule-0 un-fold decision was warranted.

### The smoke wrote to a DISPOSABLE temp vault — the real vault was never written

Phase 6.8 started the app against an **OS-temp copy** of the vault
(`be:5186/fe:5176`), clicked **P4 Defer** in the UI → the **temp** card's P4
status became `deferred` (surgical, `date` preserved), then **re-verified the REAL
vault P1–P6 are still intact / unchanged** and tore down + deleted the temp dir.
The mutation path was exercised end-to-end in a browser with **zero risk to the
source of truth.** This is the correct posture for testing a destructive surface
and should be the template for every future write story.

## 4) Systemic Issues

1. **The adversarial-freeze pattern now has TWO consecutive pre-code MAJOR catches
   (S4, S5b-1) — codify it as a process strength.** S4: the architect caught the
   Windows-drive `path.isAbsolute` traversal bypass (SEC2) before any code.
   S5b-1: the architect caught the `matter.stringify` **data-corruption** of the
   vault before any code. Both were **empirical** (the architect *ran* the suspect
   code path against reality, didn't reason about it), both were **pure freeze
   value** (zero rework), both were on **security/write-critical seams**. This is
   no longer a one-off — it is a repeatable, high-leverage practice. **Recommend
   a project-layer check that for any write- or security-critical seam, the
   architect empirically verifies the proposed mutation/containment mechanism
   against the live store and freezes named invariants + an attack table** (see
   §5, §6). This is the most valuable systemic signal of the cycle.

2. **The dedicated-5.5 Rule-0 trigger validated again — and broadened.** S4
   established "un-fold 5.5 when the story reads a **client-originated path**."
   S5b-1 confirms the broader rule the S5a RETRO predicted: **un-fold 5.5 for ANY
   vault write.** The 5.5 added zero loops (PASS) and its value was *proof* — every
   write vector traced + run live in a temp vault. The Rule-0 risk scaling is now
   validated across both axes (client-path fs **read** on S4, vault **write** on
   S5b-1). Log as a positive systemic signal: the un-fold trigger is now firmly
   *"client-path fs read OR any vault write."*

3. **Token-vs-rigor for write surfaces: the highest cost yet (~804K) is scope,
   not regression.** S5b-1 is the most expensive cycle (S1 463 / S2 450 / S3 390 /
   S4 688 / S5a 431 / **S5b-1 ~804**). Four independent, *expected* multipliers
   explain it, all correct for the first write surface: (a) **first vault-write**
   risk class (an entire WriteFirewall + 2 surgical rewriters + a service + a route
   layer), (b) a **dedicated 5.5** (a 75K-token extra subagent), (c) **parallel
   code + security reviews** (two full Phase-5 gates), and (d) the **largest test
   suite in project history** (~120 new tests, 135K-token Phase-6 run) + a 2-agent
   fix loop. **Per-run tokens stayed in-band**; the increase is *more runs and
   bigger artifacts*, not bloated agents. Benchmark future write cycles against
   S5b-1, not against the read-only S1–S3/S5a band — exactly as S4 set the
   benchmark for L read cycles.

4. **The mechanism-hedge thread (P3 / LL-011 / LL-012) recurs in a THIRD form —
   the serializer round-trip.** S2/S3: obvious forks (yaml-vs-JSON; reject-vs-coerce)
   → LL-011. S4: a platform-fact-gated fork (Node-22 symlink dirent) → LL-012.
   **S5b-1: a library-fact-gated fork** — "round-trip the parsed doc through
   `matter.stringify` to preserve it" reads as obviously-correct but is the *exact
   opposite* of byte-preserving, because the serializer re-emits the whole doc.
   This is a distinct, recurring root-cause class (state the *mechanism* of a
   structured-doc rewrite; never assume a serializer preserves) → **LL-013** (§5).
   The thread is now three lessons deep — pattern-detector should consider whether
   LL-011/012/013 want a single generalized "name the mechanism for any
   parse/classify/serialize step" umbrella.

5. **Positive: review-check §8 (React type-only imports) suppressed its
   recurrence on first deployment.** The S5a RETRO added review-check §8 to kill
   the React-namespace import MINOR (recurred S4+S5a). S5b-1 is the **first cycle
   after the check landed and the MINOR did NOT appear** — the FE used named type
   imports and the reviewer logged no such MINOR. Confirm-effectiveness data point
   for pattern-detector (the check works).

6. **Standing debts unchanged (none recurred as defects):** canonical vault
   `VERSION` file (P5, since S2), sidebar active-nav prefix-match (P6, since S2),
   dev-README `:5174`/`BACKEND_PORT` note (P2, now **6+ cycles** of the same
   workaround). None blocked S5b-1; all still cheap, batchable, overdue.

## 5) Workflow Improvements (Concrete)

1. **Codify the adversarial-freeze practice for write/security-critical seams.**
   Two consecutive pre-code MAJOR catches (S4 SEC2, S5b-1 `matter.stringify`)
   justify making this an explicit, repeatable step rather than a happy accident:
   for any seam that writes to disk, shells out, or contains a client path, the
   architect **empirically verifies the proposed mutation/containment mechanism
   against the live store** (run it; assert the actual bytes/behavior) and freezes
   **named invariants + an attack table with a "where" column**. This is what made
   both the S4 and S5b-1 5.5 reviews fast verifications instead of explorations.
   Propose as a `.claude/project/` check for the architect (and a note in the
   freeze template). See §6.

2. **Add LL-013 — byte-preservation of structured-doc rewrites.** Genuinely new,
   root-cause, cross-cutting: it will recur for **any** future doc write (S5b-2's
   apply, framework `agents/*.md` patches, any frontmatter/JSON/YAML mutation).
   The rule: **never round-trip a structured document through a serializer
   (`matter.stringify` / `JSON.stringify` / `yaml.stringify`) that re-emits the
   whole document — it silently coerces/reflows untouched fields. Mutate via
   surgical raw-line/region edits and preserve all other bytes verbatim.** This
   rises to an LL (not a review-check) because it is a reusable root-cause lesson,
   exactly the bar S3/S4 set. **Recommend LL-013 + a code-reviewer review-check.**
   Body proposed in §6.

3. **Make "disposable temp vault" the mandatory smoke posture for write surfaces.**
   S5b-1's 6.8 exercised the destructive path end-to-end in a browser against a
   temp copy and re-verified the real vault intact — the only safe way to smoke a
   mutation surface. Encode it as the write-surface smoke template (it is already
   what the freeze §10 mandated; promote it to a guardrail).

4. **Carry the standing cheap debts** (vault `VERSION`, sidebar prefix-match,
   dev-README `:5174` note) — overdue, none blocking.

## LL-013 — La reescritura de un documento estructurado DEBE preservar bytes: nunca round-trip por un serializador que re-emite el documento completo

- **REQ origen**: REQ-20260625-S5b-1 (triage write actions / setFindingCell + setFrontmatterDecision)
- **Síntoma**: La story prescribió re-ensamblar la card mutada con
  `matter.stringify(parsedBody, data)`. Verificado empíricamente que
  `matter.stringify(content, data) !== raw`: coacciona `date: 2026-06-06` → un
  timestamp ISO (`Date`), re-quotea `source` y reflowea `tags: [retro-triage]` a
  estilo bloque. CADA acción de escritura habría corrompido silenciosamente el
  `date` (y el frontmatter) de la card en disco — la peor clase de bug en la
  PRIMERA superficie de escritura al vault (silencioso, persistente, sobre la
  fuente de verdad). Capturado PRE-CÓDIGO por el architect en el freeze (2º catch
  mayor pre-código consecutivo tras S4 SEC2).
- **Causa raíz**: "round-trip el doc parseado para preservarlo" se LEE como obvio
  pero es lo contrario de preservar bytes: el serializador re-emite el documento
  ENTERO, coaccionando/reflowando campos no tocados. Es un fork gated por un hecho
  de librería (la semántica de `matter.stringify` / `JSON.stringify` /
  `yaml.stringify`), de la familia de LL-011 (fork obvio) y LL-012 (fork gated por
  plataforma) — aquí gated por librería.
- **Regla que aplica**: cuando una story/freeze describe la **reescritura de un
  documento estructurado** (frontmatter, tabla markdown, JSON, YAML), `story-refiner`
  / `architect-reviewer` declaran que la mutación se hace por **edición quirúrgica
  de línea/región sobre el texto crudo, preservando todos los demás bytes
  verbatim — NUNCA round-trip por `matter.stringify` / `JSON.stringify` /
  `yaml.stringify` ni ningún serializador que re-emita el documento completo**. El
  `architect-reviewer` verifica EMPÍRICAMENTE `serialize(parse(raw)) === raw`
  contra un archivo real antes de congelar; si es false, el mecanismo es la
  reescritura cruda. El `code-reviewer` confirma que ningún path de escritura
  llama a un serializador full-doc.
