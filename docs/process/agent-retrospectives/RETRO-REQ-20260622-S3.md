## 4) Systemic Issues

1. **Third consecutive clean cycle — the pattern library is now load-bearing.**
   S3 reused the S2 reader/compose pattern (`readProjectConfig` ≅
   `readLockVersion`; `config` composed onto `ProjectDetail` ≅ `drift`) rather
   than reinventing it. This is the strongest health signal in the run: the cost
   of the next read-only `ProjectDetail` projection (S4 Project Layer, S6
   Telemetría) is now mostly *known*, not *discovered*. **Recommendation:** when
   S4 opens, treat the S2/S3 fs-safe-read + `.extend` composition as the default
   template; deviate only where the source is genuinely heavier (a file walk vs a
   single-file read — which the S3 REQ already flagged as the point per-tab lazy
   endpoints become justified).

2. **Design-token hygiene (`--radius-card` gap) — review-check, not a new LL.**
   A CSS custom property (`--radius-card`) was referenced in a new component
   before being defined in `tokens.css`; the FE silently fell back to a literal,
   and code review caught it. This is a thin, mechanical, project-specific gap —
   it does not rise to a workflow lesson. **Recommendation:** add a one-line
   item to `.claude/project/review-checks/code-reviewer.md`: *"any CSS custom
   property (`var(--x)`) referenced by a new/edited component must be defined in
   `frontend/src/.../tokens.css`; flag undefined tokens as MINOR."* (See §6.)

3. **code-reviewer wall-time is not reliably in-band (recurring).** S1 ~25 min,
   S2 ~5.2 min, S3 ~58.5 min — high variance, with the two slow runs (S1, S3)
   both far exceeding token-proportionate time. This is the **second slow
   reviewer run in three cycles** (S2 was the exception). It is not a correctness
   defect, but it is a recurring latency cost. **Recommendation:** feed the
   reviewer a pre-extracted context digest (Rule T1: frozen schema + changed-file
   list + the specific invariants to verify) so it greps/reads less. Carry to
   the backlog; it crosses the "twice in three cycles" bar for the *latency* axis
   even though tokens stay proportionate.

4. **Standing debts unchanged (none recurred as defects):** the vault `VERSION`
   file (S2 Systemic #1), the sidebar active-nav prefix-match (S2 Systemic #2),
   and the dev-README `:5174`/`BACKEND_PORT` note (open since S1) — none blocked
   S3, none recurred as a defect, all still cheap and batchable. S3 surfaced **no
   new S3-specific follow-up** (per SMOKE-S3).

5. **Env friction (not a defect, now three cycles):** the same `:5174` Vite port
   collision, resolved again via `BACKEND_PORT=5184` (both Express and the Vite
   proxy already read it). Three consecutive cycles — the one-line dev-README
   note S1/S2 already recommended is overdue.

## 5) Workflow Improvements + Proposed Lessons

1. **T3 is validated for S-complexity read-only composition stories.** Keep
   combining Phase 1+2 when the surface is a single read-only contract
   projection with no logic/write/auth/multi-story risk (it saved ~22–45K tokens
   here at no quality cost). Keep them split otherwise. No prompt change needed —
   this is a Rule-0/T3 application note, now with one data point behind it.

2. **The recurring "story hedges a *mechanism* → architect MINOR" thread is now
   worth codifying (LL-006 extension).** This is the **third cycle** the same
   shape appears:
   - **S2:** the story left lock-parse (yaml vs JSON) and version-compare
     (segment-wise vs string) as hedged "Technical Notes" → **2 architect MINORs.**
     The S2 RETRO flagged it as a *light* note ("state parse/compare mechanism
     decisions in the story, not as hedges").
   - **S3:** the story stated permissive typing + "do not coerce" in prose but
     left the exact **type-strict reject-vs-coerce** mechanism implicit → **1
     architect MINOR** (resolved in the freeze §2).
   Each instance is individually cheap (resolved in-freeze, zero rework), but the
   *pattern* now spans S2 + S3 and is exactly LL-006's spirit (specify the exact
   syntax/operator) extended from TS-type syntax to **algorithm/curation
   mechanism**. It has crossed from "light note" to "worth a lesson." See §6 for
   the proposed **LL-011**. (LL-006 stays as-is; LL-011 generalizes it to
   mechanisms.)

3. **Design-token hygiene is a review-check, not a lesson.** The `--radius-card`
   gap is real but project-specific and mechanical — codify it as a
   `code-reviewer` project-layer check (§6, §4 item 2), **not** an LL. Promoting
   every cosmetic miss to an LL would dilute the lesson library; reserve LLs for
   process/root-cause patterns (which the mechanism-hedge thread is, and the
   token gap is not).

### Proposed addition to `docs/process/lessons-learned.md` — **one genuinely new (LL-011)**

> Suggestion for the orchestrator to apply; this subagent does not edit
> `lessons-learned.md` directly. LL-008/009/010 were *applied* this cycle, not
> newly discovered — no re-add. The `--radius-card` gap is a review-check, not
> an LL (see §6).

```markdown
## LL-011 — Stories must state the exact *mechanism* of a parse/compare/curate step, not hedge it

- **REQ origen**: REQ-20260622-S2-project-detail-drift (lock-parse / version-compare)
  y REQ-20260622-S3-project-config-tab (type-strict reject-vs-coerce de la curación)
- **Síntoma**: La story dejó la *mecánica* de un paso (cómo parsear el lock —
  yaml vs JSON; cómo comparar versiones — segmento-a-segmento vs string; cómo
  curar un slot type-strict — rechazar a `null` vs `String(value)`/coerción)
  como una "Technical Note" en prosa, no como una decisión resuelta. Cada caso
  salió como un MINOR del `architect-reviewer` (S2: 2 MINORs; S3: 1 MINOR),
  resuelto dentro del freeze sin retrabajo, pero repetido en 2 ciclos.
- **Causa raíz**: LL-006 obliga a especificar la *sintaxis* exacta de un tipo
  TypeScript (`?` vs `: T | null`), pero no cubría la *mecánica de un algoritmo*
  (parse/compare/curación). El refinador dejó la elección implícita asumiendo que
  el implementador "haría lo razonable".
- **Regla que aplica**: `story-refiner` —y `po-analyst` en modo combinado T3—
  cuando una AC nombra un paso de parse/compare/curación con más de una
  implementación razonable (yaml vs JSON; comparación numérica vs string;
  rechazo type-strict vs coerción; orden de igualdad/empate), declara la
  decisión resuelta en la AC (una línea), no una nota hedge. El
  `architect-reviewer` deja de gastar un MINOR en re-resolverla; el freeze solo
  la confirma.
```

## 7) Next-Requirement Guardrails (carry into S4 — Project Layer tab)

- **Reuse the S2/S3 read-and-compose template (Systemic #1):** S4 reads the
  project's `.claude/project/` layer. Use the fs-safe read helper shape

  via `.extend`. **But note:** S4 is a **directory file-walk**, heavier than a

  extending the default-tab payload. Re-evaluate endpoint shape in GATE0.

  `.claude/project/` shape against live files in GATE0, proactively, before the
  REQ (how many projects even have a project layer? what files? — census first).
- **Mandatory enum check (LL-008):** any field mirroring project-layer content
  is `z.string()`/open; only app-computed states are `z.enum`.
- **Mandatory mechanism check (new LL-011):** if an AC names a parse/curate/order
  mechanism with >1 reasonable implementation, state the resolved decision in the
  AC — don't hedge it into an architect MINOR.
- **Design-token check (new review-check):** any `var(--x)` a new component uses
  must be defined in `tokens.css`.
- **T3 decision:** S4's file-walk + likely per-tab endpoint makes it *less*
  obviously an S surface than S3 — evaluate Rule 0 honestly; do **not** auto-apply
  T3 if the endpoint shape or the walk logic adds real risk.
- **Freeze invariants, not just shapes** — for any stateful/derived field, freeze
  the mapping + the absent/empty rule (this is what made S3's review able to
  verify exact conformance).
